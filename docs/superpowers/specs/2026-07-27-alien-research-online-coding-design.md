# 외계 생태 연구선 온라인 코딩 게임 설계

**작성일:** 2026-07-27
**상태:** 확정
**대상:** Godot 4.6.2, Steam Windows, iOS, Android

## 1. 목표

현재의 퀴즈·캐릭터 수집 게임을 다음 방향으로 점진 전환한다.

- 게임 테마를 목장에서 **외계 생태 연구선**으로 변경한다.
- 기존 객관식·오답노트·SRS는 유지한다.
- 사용자가 Python 코드를 직접 작성하고 숨겨진 테스트로 채점받는 코딩 문제를 추가한다.
- 로컬 개발에서도 운영 환경과 같은 API·DB·Judge0 경계를 사용한다.
- 최종적으로 계정, 클라우드 저장, 랭킹, 사용자 간 캐릭터 거래를 지원한다.
- 초기 기능은 작게 출시하되 캐릭터 소유권과 경제 데이터는 처음부터 서버 권한으로 둔다.

## 2. 범위와 단계

### 2.1 1단계: 로컬 온라인 구조

- Godot 클라이언트
- 로컬 Python API
- 로컬 애플리케이션 PostgreSQL
- 로컬 Judge0 CE와 Judge0 전용 PostgreSQL·Redis
- 개발용 게스트 계정
- Python 표준 입출력 문제
- 서버 권한 지갑·캐릭터 인스턴스·보상
- 서버 API를 사용하는 NPC 시장

사용자 경험은 싱글플레이와 비슷하지만 모든 거래 가능 데이터는 서버에서 확정한다.

### 2.2 2단계: 운영 서버

- HTTPS API
- Steam, Apple, Google 로그인
- 이메일 기반 계정 복구
- 게스트 계정 승격과 플랫폼 계정 연결
- 클라우드 저장
- 코딩 제출 기록과 개념별 숙련도
- 랭킹
- 서버 기반 가챠·융합·교배

### 2.3 3단계: 사용자 시장

- 캐릭터 판매 등록
- 판매 등록 중 에스크로 잠금
- 구매·취소·만료
- 거래 수수료
- 서버 원장 기반 코인 이동
- 중복 요청·동시 구매·이중 판매 방지
- 이상 거래와 다중계정 악용 탐지

## 3. 시스템 경계

```text
Godot Client
  ├─ public problem content/cache
  ├─ code editor and draft UI
  └─ HTTPS API client
          |
          v
Game API
  ├─ authentication/account linking
  ├─ progress/mastery
  ├─ wallet and immutable ledger
  ├─ creature ownership
  ├─ rewards and idempotency
  ├─ NPC/P2P market
  └─ submission orchestration
          |
          +------> Application PostgreSQL
          |
          +------> Private Judge0 API
                         |
                         +--> Judge worker
                         +--> Judge0 PostgreSQL
                         +--> Judge0 Redis
```

Judge0는 외부 인터넷에 공개하지 않는다. Godot은 Judge0 주소, 관리자 자격증명, 정답 코드, 숨겨진 테스트를 알지 못한다.

## 4. 서버 권한 데이터

다음 데이터는 로컬 `progress.json`을 신뢰하지 않는다.

- 사용자 ID와 연결된 로그인 제공자
- 코인·가챠권·간식
- 캐릭터 인스턴스와 소유자
- 캐릭터 레벨·등급·반짝·색조
- 가챠·융합·교배 결과
- 보상 수령 기록
- 제출과 Accepted 결과
- 시장 등록과 거래

로컬 파일은 UI 설정, 다운로드한 공개 문제, 미제출 코드 초안 캐시 용도로만 사용한다.

### 4.1 핵심 테이블

```text
users
auth_identities
wallets
wallet_ledger
creature_instances
reward_claims
coding_problems
coding_problem_versions
coding_test_cases
coding_submissions
concept_mastery
drafts
market_listings
market_transactions
```

### 4.2 원장과 멱등성

모든 재화 변경은 잔액과 함께 원장에 기록한다.

```text
+3200 coding_accept_reward
-1000 gacha_pull
+2400 creature_sale
-120  market_fee
```

보상, 가챠, 융합, 교배, 판매, 구매 요청은 클라이언트가 생성한 멱등 키를 받는다. 서버는 동일 키의 두 번째 요청에 기존 결과를 반환한다.

### 4.3 캐릭터 소유권 상태

```text
owned -> listed -> sold
  |        |
  |        +-> owned (cancel/expire)
  +-> consumed (fusion)
```

`listed` 상태의 캐릭터는 성장, 융합, 교배, NPC 판매가 불가능하다.

## 5. 계정과 플랫폼

내부 사용자 UUID는 로그인 제공자와 분리한다.

- Steam Windows: Steam 인증 연결
- iOS: Apple 인증 연결
- Android: Google 인증 연결
- 공통: 이메일 복구
- 로컬 개발: 게스트 계정

게스트 계정은 정식 계정으로 승격할 수 있다. 하나의 사용자 UUID에 여러 플랫폼 인증을 연결할 수 있다. 계정 병합은 서버 트랜잭션으로 처리하며 자동 병합하지 않는다.

## 6. 코딩 문제 형식

### 6.1 1차 지원 범위

- 언어: Python
- 채점 방식: 표준 입력·표준 출력
- 공개 예제 실행과 최종 제출 분리
- 최종 제출은 숨겨진 테스트 포함
- 결과: Accepted, Wrong Answer, Runtime Error, Time Limit, Memory Limit, Output Limit, Internal Error

함수명 강제 방식은 1차 범위에서 제외한다. 입력을 읽고 결과를 출력하는 방식이 언어 확장과 격리에 유리하다.

### 6.2 공개 문제 스키마

```json
{
  "id": "frequency-kit-001",
  "version": 1,
  "title": "생체 표본 키트 조립",
  "concepts": ["hash-map", "frequency-count", "multiset"],
  "stage": "practice",
  "language": "python",
  "statement": "...",
  "input_format": "...",
  "output_format": "...",
  "constraints": ["1 <= len(target) <= 200000"],
  "examples": [
    {"input": "abc\nabccda\n", "output": "1\n"}
  ],
  "starter_code": "target = input().strip()\ntext = input().strip()\n",
  "time_limit_ms": 2000,
  "memory_limit_kb": 131072
}
```

정답 코드, 숨겨진 테스트, 오답 변형, 보상 정책은 클라이언트 데이터에 포함하지 않는다.

### 6.3 대표 문제

`target`을 구성하는 문자 세트를 `text`의 문자로 최대 몇 번 만들 수 있는지 구한다. 순서는 관계없고 사용한 문자는 재사용할 수 없다.

```text
abc / abccda       -> 1
aabc / aaaabbcc    -> 2
abc / abb          -> 0
aa / aaaaa         -> 2
xyz / xyzxyzxyz    -> 3
```

목표 해법은 각 문자 빈도를 센 뒤 다음 값의 최솟값을 구한다.

```text
available[character] // required[character]
```

대표 오답은 `set`으로 중복을 제거하는 풀이, 연속 부분문자열만 세는 풀이, 최솟값 대신 합계를 사용하는 풀이, `target`의 중복 문자를 무시하는 풀이이다.

## 7. Judge0 연동

### 7.1 제출 흐름

1. Godot이 문제 ID, 버전, 언어, 코드, 멱등 키를 Game API에 보낸다.
2. API가 사용자, 문제 버전, 제출 빈도, 코드 크기를 검증한다.
3. 공개 실행이면 공개 테스트만, 최종 제출이면 서버의 숨겨진 테스트까지 선택한다.
4. API가 테스트별 표준 입력으로 Judge0 제출을 생성한다.
5. API가 Judge0 상태를 조회하고 출력을 정규화한다.
6. 모든 필수 테스트가 통과하면 Accepted를 기록한다.
7. 최초 Accepted인 경우에만 보상 트랜잭션을 생성한다.
8. Godot에는 정규화된 결과와 공개 가능한 실패 정보만 반환한다.

### 7.2 보안 제한

- Judge0는 별도 VM 또는 격리 호스트에서 실행한다.
- Judge0 포트는 사설 네트워크에서만 접근한다.
- 실행 코드의 네트워크 접근을 비활성화한다.
- CPU, wall time, 메모리, 프로세스 수, 파일 크기, 출력 크기를 제한한다.
- 제출 코드와 로그에 자격증명을 전달하지 않는다.
- 백엔드와 Judge0 데이터베이스를 분리한다.
- 운영 비밀은 Judge0 워커에 마운트하지 않는다.
- 사용자별·IP별·계정별 제출 속도 제한을 적용한다.

Judge0 CE의 GPLv3 조건과 배포 방식은 운영 배포 전에 별도 라이선스 검토를 수행한다.

### 7.3 언어 확장

문제와 제출은 내부 `language_key`를 사용하고, 서버가 Judge0 `language_id`로 변환한다.

```text
python -> javascript -> java -> cpp
```

언어 추가 시 스타터 코드, 출력 정규화, 컴파일 제한, 기준 풀이, 변형 오답을 별도로 검증한다.

## 8. 적응형 학습

### 8.1 네 단계

1. **학습형:** 쉬운 설명, 단계별 힌트, 스타터 코드, 시간 제한 없음
2. **연습형:** 함수 골격 또는 입력 골격, 공개·숨겨진 테스트, 선택적 힌트
3. **면접형:** 제한된 힌트, 접근 방법 설명, 복잡도 질문, 선택형 꼬리질문
4. **도전형:** 큰 입력, 성능 테스트, 엄격한 제한, 힌트 없음

### 8.2 숙련도

개념별로 별도 숙련도를 저장한다.

- 첫 제출 성공 여부
- 제출 횟수
- 힌트 단계
- 오류 종류
- 공개 테스트와 숨겨진 테스트 결과
- 복잡도 질문
- 일정 기간 후 변형 문제 재풀이

오답 후 같은 문장을 반복하지 않고 동일 개념의 다른 변형을 SRS 일정에 맞춰 추천한다.

### 8.3 무처벌 원칙

- 오답으로 캐릭터, 재화, 스트릭을 잃지 않는다.
- 실패 시 더 쉬운 설명과 관련 문제를 추천한다.
- 정답 확인 후에도 다음 변형 문제에서 전체 보상을 받을 수 있다.
- 동일 문제의 최초 Accepted만 거래 가능 보상을 지급한다.

## 9. 문제 데이터 증강

사용자가 승인한 개인 Obsidian 노트의 52문제·17유형을 시드 자료로 사용한다. 원문은 저장소나 운영 서버에 복사하지 않는다.

### 9.1 추출 대상

- 알고리즘 개념
- 풀이 사고 단계
- 목표 시간·공간복잡도
- 엣지 케이스
- 대표 오답
- 면접 꼬리질문

### 9.2 생성 대상

- 독자적인 문제 제목과 세계관
- 독자적인 입력값과 예제
- 학습·연습·면접·도전 변형
- 공개 테스트
- 숨겨진 엣지 테스트
- 성능 테스트
- Python 기준 풀이
- 대표 오답 코드
- 단계별 힌트
- 복잡도·꼬리질문

### 9.3 규모

- 파일럿: 대표 시드 12개, 시드당 3~4변형, 36~48문제
- 품질 검증 후: 52개 시드를 개념 적합성에 따라 3~4변형, 156~208문제

모든 시드에 억지로 도전형을 만들지 않는다. 성능 차이가 의미 없는 문제는 세 단계만 제공한다.

### 9.4 검증 파이프라인

1. Researcher가 시드의 개념과 경계 조건을 구조화한다.
2. Author가 독자 문제, 기준 풀이, 테스트, 대표 오답을 작성한다.
3. Verifier가 기준 풀이와 설명을 검토한다.
4. Judge0에서 기준 풀이가 모든 테스트를 통과하는지 확인한다.
5. 변형 오답을 실행해 숨겨진 테스트가 실제 실수를 잡는지 확인한다.
6. 유사도 검사로 문제 문구·예제 중복을 확인한다.
7. 사람이 난이도, 명확성, 저작권, 교육 가치를 승인한다.

자동 생성 결과는 사람 승인 전 공개하지 않는다.

## 10. Steam과 모바일 역할

### 10.1 Steam Windows

- 전체 코드 편집기
- 면접형·도전형
- 키보드 중심 단축키
- 테스트 결과와 실행 로그 비교
- 복잡도와 꼬리질문

### 10.2 모바일

- 학습형·연습형
- 짧은 코드 작성
- 오답 복습
- 힌트·해설·코드 읽기
- 진행 상황과 캐릭터 관리
- 긴 문제는 Steam에서 이어 풀기

모바일에서 긴 문제를 차단하지는 않지만 추천하지 않는다. 코드 초안과 커서 복원에 필요한 최소 상태를 서버에 저장해 Steam에서 이어서 편집한다.

## 11. 게임과 학습 연결

```text
학습형 통과 -> 표본 발견
연습형 통과 -> 생명체 부화
면접형 통과 -> 유전자 안정화·등급 성장
도전형 통과 -> 희귀 변이·연구선 구역 해금
SRS 복습 성공 -> 성장·신뢰도 상승
GitHub 활동 -> 보조 에너지·간식
```

학습 보상은 서버가 Accepted 기록을 근거로 지급한다. 코딩 제출을 반복해 재화를 채굴할 수 없다.

## 12. 아트 방향

### 12.1 스타일

고품질 비픽셀 **생체발광 과학도감형**을 사용한다.

- 2.5D 일러스트 또는 고품질 렌더 기반 투명 PNG
- 반투명 젤, 깨끗한 유리, 결정, 꽃잎 재질
- 장기 표현 대신 별빛 에너지 무늬
- 숯색·오프화이트 기반에 청록·산호·라임·호박색을 기능별로 사용
- 연구선 관측창, 표본 캡슐, 생태 도감, 스캔 UI
- 작은 모바일 화면에서도 읽히는 실루엣

### 12.2 감정 구성

24종 기준:

- 친근형 10종
- 장난스러운 기묘형 5종
- 신비형 4종
- 장엄형 3종
- 심연형 2종

심연형은 고어가 아니라 아름답고 불길한 코즈믹 언캐니로 제한한다. 점프스케어, 피, 상처, 점액, 기생충, 실제 장기, 피부 구멍, 인간형 치아를 사용하지 않는다.

### 12.3 형태군

기본 형태:

- 식물
- 유동
- 광물
- 천체

특수 형태:

- 의태
- 군체
- 공생

희귀 형태:

- 심연

형태군은 1차 버전에서 전투 속성이나 상성을 만들지 않는다. 외형, 랜덤 행동, 교배 파츠에만 영향을 준다.

### 12.4 캐릭터 검수

- 첫인상이 친근함·호기심·신비함·장엄함·의도된 불길함 중 하나인지 확인
- 질병·기생·혐오 연상이 의도하지 않게 발생하면 폐기
- 128px에서도 얼굴과 실루엣이 읽히는지 확인
- 24종 사이의 실루엣 중복 확인
- 기존 유명 캐릭터와 혼동 가능성 확인
- 생성 프롬프트와 생성·수정 기록 보존

## 13. 제작 도구

### 13.1 Godot AI MCP

- Godot 4.6 편집기와 로컬 연결
- 씬 트리·노드·실행 로그 검사
- 실제 게임 실행과 화면 캡처
- 클릭·입력 기반 스모크 테스트
- 외부 코드는 버전을 고정하고 라이선스·보안 검토 후 추가
- MCP 서버는 개발 환경의 loopback에만 바인딩
- 편집기 도구는 운영 빌드에 포함하지 않음

### 13.2 imagegen과 Creative Production

- Creative Production 보드에서 형태군별 탐색을 관리
- imagegen으로 후보를 생성
- 접촉 시트에서 실루엣·재질·표정·IP 유사성을 비교
- 사람 검수 후 선택된 원화만 저장소에 반영

### 13.3 Figma

설계 대상:

- 연구선 홈과 생태실
- Steam 코딩 작업 공간
- 모바일 학습·복습 화면
- 캐릭터 도감과 상세
- 가챠·부화
- NPC·사용자 시장
- 제출 결과·숙련도

Godot 구현 전에 데스크톱과 모바일 핵심 화면을 같은 디자인 토큰으로 검증한다.

## 14. 기존 프로젝트 전환

### 14.1 즉시 안정화

- 목장 OFF에서 `_yard == null`인데 정렬 타이머가 실행되는 오류를 회귀 테스트로 재현하고 수정한다.
- 정체불명의 미추적 파일은 내용을 읽거나 자동 삭제하지 않고 정확한 이름으로 Git 추적에서 제외한다.
- 현재 129개 테스트와 메인 씬 스모크 테스트를 유지한다.

### 14.2 호환

- 기존 객관식 JSON 스키마는 유지한다.
- 코딩 문제는 별도 서버 스키마로 시작한다.
- 기존 SRS는 `concept_mastery`와 연결하되 로컬 학습 기록을 즉시 삭제하지 않는다.
- 공개 출시 전 개발 세이브의 거래 가능 재화는 자동 신뢰 이전하지 않는다.
- 필요한 경우 개발자 계정에 한해 관리 도구로 이전한다.

- 운영 게임에 Godot MCP 포함

## 17. 성공 기준

- 로컬 Docker 환경에서 Godot이 Python 문제를 실행·제출할 수 있다.
- 숨겨진 테스트와 정답은 Godot 프로젝트에 존재하지 않는다.
- 최초 Accepted만 서버 권한 보상을 지급한다.
- 네트워크 재시도로 중복 보상이 발생하지 않는다.
- 기존 객관식·SRS·캐릭터 기능이 유지된다.
- 목장 OFF 메인 씬이 오류 없이 실행된다.
- 12개 시드의 36~48문제 파일럿이 기준 풀이·오답 변형 검증을 통과한다.
- Steam 코딩 화면과 모바일 학습 화면이 Figma와 Godot에서 검증된다.
- 캐릭터 후보는 형태군·혐오감·IP 유사성 검수를 통과한다.
- NPC 시장으로 시작해도 같은 캐릭터 인스턴스·원장 구조로 사용자 시장을 추가할 수 있다.
